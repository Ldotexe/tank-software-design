# Tank software design

Учебный проект на LibGDX. Управление: стрелки или WASD, выстрел — отдельное нажатие пробела. Клавиша L скрывает и показывает полоски здоровья, изначально они видны. Деревья и другие танки блокируют движение. Танк игрока ярко-синий, AI-танки темнее.

## Запуск

Проект проверен с JDK 17. Если установлено несколько версий Java, выберите JDK 17 через `JAVA_HOME`.

```bash
bash gradlew run
bash gradlew test
bash gradlew build
```

Отчёт о тестах: `build/reports/tests/test/index.html`. Для unit-тестов не нужны окно и OpenGL.

## Структура

- `app` — запуск приложения и создание объектов игры.
- `game` — игровой цикл и интерфейсы ввода, обновления и отображения.
- `model` — танк, поле, препятствия и правила движения.
- `input` — обработка клавиатуры и привязки управления.
- `command` — команды движения, стрельбы и переключения полосок здоровья.
- `control` — стратегии управления танками и контроллеры.
- `graphics` — слои отрисовки и изображения объектов.
- `graphics.util` — интерполяция и расчёты экранных координат.

## Hometask 3

`Tank` получает `MovementRules` и длительность перехода через конструктор. `GameField` реализует эти правила и проверяет коллекцию `Obstacle`, поэтому для нового препятствия не нужно менять поле или танк.

`GameSession` обновляет актуальные объекты логического уровня, включая появившиеся пули. `GameLoop` зависит от интерфейсов `CommandSource`, `Updatable` и `GameView`. Его можно использовать с другим вводом или без графического окна.

`GameRenderer` рисует список `RenderLayer`. `ObservedObjectLayer` получает объекты через события логического уровня. `FieldRenderer` рисует карту, а `ObjectLayer<T>` — группу объектов через `ObjectRenderer<T>`. Для нового типа объекта достаточно реализовать его отрисовщик и подключить слой. Один отрисовщик с одной текстурой обслуживает всю группу объектов.

Длительность движения, пути к ресурсам и создание конкретных объектов находятся в `DefaultGameFactory`. Начальное расположение объектов передаётся через описание уровня. Чтобы добавить препятствие с изображением, нужно зарегистрировать его в поле и подключить соответствующую группу к отрисовке. Пути к текстурам и интерполяция передаются отрисовщикам через конструкторы.

`KeyboardHandler` позволяет добавлять действия на удержание (`bindHeld`) и однократное нажатие (`bindJustPressed`). `PlayerControls` принимает функцию движения, а не конкретный танк.

Сохранены управление, поворот перед препятствием и длительность движения (0.4 секунды). Выход за края карты запрещён.

Тесты проверяют исходное поведение, замену правил движения, разные длительности перехода, препятствия из нескольких клеток, добавление обновляемых объектов, порядок игрового цикла и подключение новых слоёв отрисовки.

## Hometask 4

Добавлены два источника наполнения уровня: случайная генерация и чтение текстового файла. Они реализуют `LevelSource` и возвращают `LevelLayout` с размерами поля, деревьями и начальной позицией игрока. Сборка игры использует это описание для проверки препятствий и отрисовки.

Без аргументов создаётся случайное поле 10×8 с 20 деревьями. Можно выбрать режим и параметры:

```bash
bash gradlew run --args='--random'
bash gradlew run --args='--random 12 7 25'
bash gradlew run --args='--level src/main/resources/level.txt'
```

В текстовом файле `T` обозначает дерево, `X` — начальную позицию игрока, `_` — пустую клетку. Файл должен содержать непустое прямоугольное поле и ровно один `X`. Первая строка соответствует верхнему ряду. Пример из презентации находится в `src/main/resources/level.txt`.

Случайный генератор выбирает разные клетки для деревьев и игрока. Количество деревьев должно быть меньше количества клеток. Фон подстраивается под размеры уровня. Начальное окно имеет размер 960×640; весь уровень масштабируется под окно с сохранением пропорций, в том числе при изменении его размера. При движении проверяются препятствия, другие танки и границы поля.


## Hometask 5

На свободных клетках случайно размещаются AI-танки. Игрок начинает на позиции `X` из файла или на позиции, выбранной генератором уровня. По умолчанию создаются 3 AI-танка; количество задаётся через `--bots`:

```bash
bash gradlew run --args='--random --bots 5'
bash gradlew run --args='--level src/main/resources/level.txt --bots 3'
bash gradlew run --args='--random 1 1 0 --bots 0'
```

Если свободных клеток не хватает для указанного количества танков, игра сообщает об ошибке до открытия окна. Для маленькой карты можно выбрать меньше танков или `--bots 0`.

`TankSpawner` создаёт танки, регистрирует их в общем `GameField` и возвращает `TankGroup` с игроком и AI. Поле знает свои размеры и блокирует выход за них. Пока танк движется, он занимает исходную клетку и клетку назначения; исходная освобождается только после завершения перехода.

`MoveCommand` выполняет движение танка. `KeyboardControlStrategy` выбирает команды по стрелкам/WASD, `RandomControlStrategy` — по случайному направлению. `TankController` запрашивает команды у живого танка; на ходу доступны выстрелы, новые команды движения ждут завершения перехода. Сначала обрабатываются команды всех контроллеров, затем обновляются позиции, поэтому занятость клеток учитывается между всеми танками.

Тесты проверяют размещение, команды, стратегии, границы, столкновения и занятость обеих клеток. Дополнительно проверяется длительная симуляция движения нескольких AI без графики.


## Hometask 6

Добавлены `ShootCommand`, пули и здоровье танков. Игрок стреляет по отдельному нажатию пробела, AI случайно выбирает движение или выстрел. Стрелять можно на ходу. Рекомендательный движок не используется согласно уточнению преподавателя.

По умолчанию у танка 100 здоровья, пуля наносит 25 урона и проходит клетку за 0.1 секунды. Параметры задаются через конструкторы `Tank` и `BulletSettings`; `TankSpawner` принимает их при создании группы. Согласно формулировке задания танк удаляется при здоровье ниже нуля; при нуле он ещё действует.

Пуля создаётся в следующей клетке по направлению танка и игнорирует своего владельца. При попадании в дерево, танк, другую пулю или границу уровня она удаляется. Танк получает урон один раз, дерево остаётся на месте. Столкновения проверяются и в клетке появления пули, поэтому выстрел вплотную сразу попадает в цель.

`GameField` хранит логические объекты и сообщает `LevelListener` об их добавлении и удалении. При подписке передаются уже существующие объекты через те же уведомления. Так графика получает и начальное состояние, и изменения во время игры. `ObservedObjectLayer` подписывается на эти события, а при закрытии игры отписывается и освобождает общий отрисовщик.

Кадр состоит из четырёх этапов: сбор всех команд, выполнение, обновление объектов и отрисовка. При обновлении используются снимки коллекций; удалённые объекты больше не обновляются и не выполняют команды. Движение пуль обрабатывается по промежуточным событиям, чтобы большой временной шаг не позволял пролетать сквозь препятствия.

Прежние команды запуска подходят и для стрельбы:

```bash
bash gradlew run --args='--level src/main/resources/level.txt --bots 3'
bash gradlew run --args='--random --bots 5'
```

## Hometask 7

У каждого танка хранится максимальное здоровье, равное начальному. Полоски здоровья игрока и AI видны сразу. Клавиша L скрывает или показывает их одним нажатием; удержание не переключает состояние повторно.

`ToggleHealthBarsCommand` меняет общее состояние `HealthBarVisibility`. `GameControls` собирает эту команду отдельно от управления танками, поэтому L работает и после гибели игрока. Команда выполняется на обычном этапе выполнения команд игрового цикла.

`HealthBarRenderer` — декоратор `ObjectRenderer<Tank>`: сначала вызывает вложенный отрисовщик танка, затем рисует полоску текущего здоровья. Её положение интерполируется так же, как положение танка. При нулевом здоровье полоска пустая. Новые и удалённые танки обрабатываются существующим `ObservedObjectLayer`.

## Hometask 8

Поведение танка зависит от доли оставшегося начального здоровья:

- Больше 70% — обычная скорость, стрельба доступна.
- От 15% до 70% включительно — движение вдвое медленнее, стрельба доступна.
- Меньше 15% — движение втрое медленнее, стрельба запрещена.

Используется шаблон State: танк делегирует текущему состоянию выбор скорости и выполнение выстрела. Команды и стратегии управления не проверяют проценты здоровья. Новое поведение можно добавить отдельным состоянием: оно само решает, когда выполнять переданное действие выстрела, и как реагировать на урон. Пороги считаются относительно `getMaxHealth()`, поэтому одинаково работают для танков с разным начальным здоровьем. Прежнее правило удаления сохранено: танк с нулевым здоровьем остаётся на уровне, с отрицательным удаляется.

При попадании на ходу уже пройденная часть пути сохраняется, а оставшаяся проходится с новой скоростью. `GameSession` учитывает её при расчёте промежуточных шагов симуляции. Для танка с нулевым начальным здоровьем выбирается тяжёлое состояние.

## Архитектура: порты и адаптеры

Порты и адаптеры отмечены коротким Javadoc у объявлений классов и интерфейсов. Порт задаёт способ взаимодействия с ядром игры, адаптер связывает этот способ с внешним вводом, файлами или LibGDX. Класс тоже может быть портом: отдельный интерфейс для этого не обязателен.

### Domain

`model` содержит сущности `Tank`, `Bullet`, `Tree`, `GameObject`, поле `GameField`, параметры `BulletSettings` и направление `Direction`. `GameSession` и `BulletSimulation` выполняют доменную симуляцию: перемещение, столкновения, урон и удаление объектов. Состояния танка также относятся к domain.

`MovementRules`, `EntityWorld`, `Obstacle` и `Updatable` — внутренние контракты модели. Они описывают правила движения, мир, занятость клеток и обновление объектов. `LevelLayout` описывает логическое наполнение уровня, `TankGroup` хранит созданную группу танков. Эти классы не читают файлы и не создают графические ресурсы.

### Application

`GameLoop` организует кадр: сбор команд, выполнение, обновление модели и отображение. `command` содержит прикладные действия. `TankController`, `TankControlStrategy` и `RandomControlStrategy` выбирают команды для танков, `TankSpawner` создаёт начальную группу. `HealthBarVisibility` хранит состояние прикладной команды переключения полосок.

`CommandSource`, `GameView` и `LevelSource` задают нужные приложению способы получения команд, отображения и загрузки уровня. `LevelListener` — порт событий, исходящих из domain.

### Infrastructure

`graphics` и `graphics.util` содержат реализацию отображения на LibGDX. `input` и `KeyboardControlStrategy` переводят клавиатурный ввод в команды. `FileLevelSource` и `RandomLevelSource` предоставляют описание уровня через `LevelSource`.

`TankGame` связывает жизненный цикл LibGDX с игрой. `GameDesktopLauncher`, `GameOptions` и `LevelSourceSelector` относятся к запуску и обработке аргументов командной строки. `DefaultGameFactory` собирает модель, контроллеры и графические адаптеры. Названия пакетов здесь не определяют архитектурный слой: например, в `level` находятся и описание уровня, и файловый адаптер.

### Границы

- `GameLoop` — входной порт обновления игры; `TankGame` — его адаптер для жизненного цикла LibGDX.
- `CommandSource` — порт, через который игровой цикл запрашивает команды; `GameControls` предоставляет клавиатурные команды. `TankController` реализует тот же контракт внутри приложения: реализация интерфейса порта сама по себе не делает класс инфраструктурным адаптером.
- `GameView` — выходной порт отображения; `GameRenderer` — графический адаптер.
- `LevelSource` — выходной порт получения описания уровня; `FileLevelSource` и `RandomLevelSource` — два его адаптера.
- `LevelListener` — выходной порт событий модели; `ObservedObjectLayer` — адаптер, обновляющий графический слой по этим событиям.

`KeyboardControlStrategy` — клавиатурная часть входного адаптера управления танком. `KeyboardHandler` и `PlayerControls` помогают обрабатывать и связывать клавиши. `InputHandler` используется внутри этой обработки. `ObjectRenderer` и `RenderLayer` — внутренние интерфейсы графической реализации. Эти вспомогательные интерфейсы, как и доменные контракты, не объявляются отдельными архитектурными портами.

### Что можно улучшить

- Модель использует `GridPoint2` из LibGDX. Для полной независимости от библиотеки координаты можно представить собственным доменным типом и преобразовывать их в графическом адаптере.
- `ObservedObjectLayer` подписывается на конкретный `GameField`. Узкий порт чтения уровня и подписки на события позволил бы менять реализацию поля без изменения графического адаптера.
- `TankGame` зависит от конкретного `GameLoop`. Если потребуется другая реализация игрового цикла, его входной API можно выделить в интерфейс.
- `LevelSource` объявляет `IOException`, хотя этим портом пользуются и источники без файлов. Собственная ошибка загрузки уровня убрала бы файловую подробность из контракта.
- Пакеты `control`, `level`, `game` и `app` объединяют классы разных архитектурных ролей. При дальнейшем развитии их можно разнести по слоям; сейчас роли описаны явно, без полной перестройки проекта.
